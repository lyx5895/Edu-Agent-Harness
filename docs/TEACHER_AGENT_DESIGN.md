## 1. 背景与已经确定的决定

现有系统（v0.10）是一个**学生辅导** harness：学生作答，系统判定、追问、给提示、做独立检查。代码和评测的大部分投入都在学生端。新的方向以教师为中心，因此先确定以下四点：

1. **先做教师端。** 学生端（辅导对话、提示阶梯、独立检查、复习计划）冻结，只修 bug，不再优化。
2. **保留判定的可靠性。** 现有系统最有价值的部分是作答判定：引用学生原文、工具验证、交叉复核、转教师复核，实测误判率 1.5–2%。这部分从学生会话中抽出来，作为批改的底座。
3. **开发阶段用成熟的大模型。** 出题、判题不再使用 OmniEdu-9B，统一通过模型网关（`https://lightingtheword.com/v1`，兼容 OpenAI 接口）调用，当前默认模型是 DeepSeek-V4.1-Flash（见 8.2）。等功能稳定、评测集建好以后，再评估是否换回自有模型。
4. **系统保持独立，同时向 coursemaker 贡献功能。** 核心逻辑写成不依赖 Web 框架的 Python 包，供本仓库的独立服务和 coursemaker 共同使用。
5. **覆盖 10 个科目。** 高中 9 科（语文、数学、英语、物理、化学、生物、思想政治、历史、地理）加上人工智能，每个科目都要具备全部基础功能。判定方式按**题型**选择，学科差异通过"学科包"配置（见 6.1）。

## 2. 目标与非目标

### 首版目标

- 老师在一个**课程项目**里，用自己的材料完成：**确认教学目标 → 出题改题 → 作业批改 → 学情分析**，每一步都能接着上一步做。
- 10 个科目都能走通这四步。每个科目至少支持它的常见题型；不同题型的判定可靠程度不同，在界面上如实标注（见 6.1）。
- 每个结果都能看到依据：参考了哪些材料、哪一版题目和评分标准、哪些学生作答。
- 修改题目或评分标准后，系统能指出哪些批改和分析需要更新。
- 批改的可靠性不低于现有系统：判定必须引用作答原文；没把握的转老师；老师可以改判。
- 留下可以导出的研究记录：输入、模型回答、教师选择与修改、材料来源。

### 首版不做

- 学生端功能，包括学生登录、领任务、提示和讲解。批改所需的学生作答由**老师导入**。
- （2026-11-19 更新）讲题答疑（讲评稿）和备课设计中的重点难点与课堂活动已提前实现，界面五个标签页严格对应闭环的 01–05；“优化后续备课”（05 → 01）实现为“新建下一课时”：新项目记 `prev_project_id`，并把上一课时已确认的问题模式（含两轮对比结果）、学情概述、讲评重点和目标冻结为 `carryover` 快照；`draft_lesson_plan` 的上下文白名单新增 `carryover`，“已参考”显示“上一课时学情”。
- 课件、视频生成。这些 coursemaker 已经有了，我们不做。
- 模型训练，以及换回 OmniEdu。

## 3. 核心概念

| 概念 | 含义 |
|---|---|
| **课程项目** | 工作的基本单位，例如"高一数学｜对数函数｜第 2 课时"。所有材料、产物、学生名单都属于某个项目 |
| **材料** | 老师上传或粘贴的教材、讲义、试卷等。每份材料有一个**材料家族编号**：同一份材料以及从它改编出的内容属于同一家族 |
| **产物** | 每一步的结果：教学目标、题目、评分标准、学生作答、批改、学情分析……每份产物都有类型、版本、状态和上游引用 |
| **版本** | 产物一旦确认就不再修改，修改即生成新版本。同一道题的各个版本共享一个"谱系编号" |
| **上游引用** | 产物生成时用到了哪些上游产物的哪个版本，同时记录内容哈希 |
| **确认** | 老师采用某个版本。只有确认过的产物才能自动传给下一步 |
| **过期** | 上游有了新的实质性版本，下游产物被标记为"依据已变化"，等待老师处理 |
| **上下文白名单** | 每类任务允许模型看到哪些产物。由代码强制执行，不靠提示词约定 |
| **题型** | 选择、填空、计算、简答与材料分析、写作等。决定用哪种判定方式 |
| **问题模式** | 学情分析找出的一类问题，例如"知道定义域条件但应用时漏掉"。它是有固定编号的产物，挂在某个目标和若干评分要点上，可以跨轮次追踪 |
| **错误标签** | 批改时为每个失分点打的标签，从学科包的错误分类中选；选不到时填"其他"并附一句描述 |
| **学生名单** | 项目内的学生代号列表。多轮作答按名单匹配到同一个学生 |
| **学科包** | 每个学科的配置：常用题型、可用的验证工具、评分标准模板、学情分析常用的错误分类、作答和反馈的语言 |

## 4. 工作流

```
 ┌────────────┐  按目标出题  ┌────────────┐  导入作答  ┌────────────┐  汇总  ┌────────────┐
 │ ① 教学目标 │ ───────────► │ ② 出题改题 │ ─────────► │ ③ 作业批改 │ ─────► │ ④ 学情分析 │
 └────────────┘              └─────▲──────┘            └─────▲──────┘        └─────┬──────┘
                                   │                         │ 第二轮作答          │ 问题模式
                                   │    ⑤ 巩固练习（第二期）  │                     │
                                   └──────────◄──────────────┴──────────◄──────────┘
                                   按问题模式出题 → 批改 → 对比同一问题模式前后的出现情况
```

**闭环怎样合上：** 学情分析产出有编号的问题模式；巩固练习按问题模式出题，每个评分要点注明针对哪个问题模式；第二轮批改的错误标签对回同一批问题模式，服务器计算每个问题模式在两轮中涉及的学生和比例，回答"巩固之后这个问题还在不在"。讲评稿（第三期）同样以问题模式为输入。

**每一步都可以单独进入，包括带着现成试卷进门：**
- **导入现成试卷：** 老师上传或粘贴试卷和答案（文字、文字版 PDF、照片）。模型拆分成题目，并起草评分要点和对应的教学目标，老师核对后确认。这些产物的来源标为 `imported`，评分要点和目标标为"由导入反推"。
- **学生名单：** 首次导入作答时建立名单；之后每轮导入按名单匹配，匹配不上的提示老师处理，不自动新建。
- 进入任何一步时，系统都会提示补齐缺少的材料，例如没有评分标准时先起草评分要点。

### ① 确认教学目标

- **输入：** 项目背景（学科、年级、课时）、老师提供的材料或教案。
- **模型：** 起草 2–5 条可检验的教学目标，每条附一句"怎样算达成"。
- **老师：** 编辑、增删后确认。
- **产物：** `objective`（每条目标一个产物）。
- **在 coursemaker 中：** 从该课时的 `lessonPlan` 和讲义中提取，见第 10 节。

### ② 出题改题

- **允许看到：** 已确认的目标、材料、题型和难度要求、老师的特别说明。
- **模型：** 每个目标生成若干题目，每道题包括题干、参考答案、分项评分要点（每项有分值）以及对应的目标。
- **服务器校验（出题自检）：**
  1. 用**另一个模型**在不看参考答案的情况下解题，再用第 6 节的批改流程对照参考答案判定。判不一致就标为"答案存疑"。
  2. 能用工具验证的（按题型，见 6.1），用工具验证参考答案。
  3. 检查评分要点：分值之和等于满分，每项要点都对应到目标。
- **老师：** 逐题编辑、删除、重新生成；可以选择 A/B 候选（第 7 节）。确认后，题目和评分标准各自成为一个确认版本。
- **产物：** `question`、`rubric`（评分标准单独成为产物，修改它不影响题目本身的版本）。

### ③ 作业批改

- **作答导入（首版）：**
  - 表格或文本：每行是"学生代号、题号、作答"，支持 CSV 和粘贴。
  - 单个学生的作答照片：识别成文字，老师核对后确认。整张试卷照片按题切分放到第二期。
- **允许看到：** 该题已确认的题目版本、评分标准版本、参考答案、这位学生对这道题的作答。**不能看到**这位学生的其他作答、历史表现或其他学生的作答，避免判定受偏见影响。
- **批改流程：** 见第 6 节。输出每个评分要点的得失分、引用的作答原文、错误位置和置信度，**每个失分点再附一个错误标签**（从学科包的错误分类中选，选不到填"其他"并写一句描述）。巩固练习的批改还要标明失分点对应哪个问题模式。
- **老师：** 待复核的批改按风险排序；老师可以确认，也可以改判，改判会生成新的批改版本，同时保留原判。不在复核队列里的批改可以批量确认。
- **产物：** `submission`（作答）、`grading`（批改）。

### ④ 学情分析

- **允许看到：** 已确认的批改（包括老师的改判）、题目所考查的目标、作答原文。
- **职责划分：**
  - **服务器**统计：每道题、每个评分要点的得分率；按错误标签汇总，每个标签涉及哪些学生、哪些作答。
  - **模型**负责：给汇总后的错误命名，把相近的标签和"其他"类归并成若干"问题模式"（例如"知道定义域条件但应用时漏掉"），每个模式必须列出支持它的作答编号和原文。因为标签在批改时已经打好，模型不必通读全班作答。
  - **服务器**核对：引用的作答编号必须存在，原文必须能在作答中找到，否则丢弃这个模式。
- **问题模式是产物：** 老师确认后获得固定编号，挂在目标和评分要点上。后续轮次沿用同一编号，不再每次重新命名；新出现的问题才新建模式。
- **证据不足时：** 如果某个区分（例如"应用时漏掉"还是"概念本身理解错"）没有足够的作答支持，就不下结论，而是生成"补查问题"供老师使用。
- **没有作答时：** 只能输出"可能的易错点"，界面明确标注"未基于学生作答"。
- **产物：** `analysis`、`problem_pattern`。

### ⑤ 巩固练习（第二期）

- **允许看到：** 已确认的问题模式及其支持作答（只给代表性的原文片段）、对应的目标和原题。
- **模型：** 针对选定的问题模式出题，复用第 ② 步的出题和自检流程。每个评分要点注明针对的问题模式。
- **批改：** 复用第 ③ 步。
- **对比：** 服务器计算每个问题模式在两轮中的出现情况（全班和个人），列出"已改善""仍存在""新出现"。证据不足时同样不下结论。
- **产物：** `question`、`rubric`（标明针对的问题模式），以及 `comparison`（两轮对比）。

### "接着做"和"已参考"

- 每一步完成后显示下一步按钮，例如"按本课目标出题""汇总学情"。
- 进入下一步时显示一条提示，例如"已参考：教学目标 3 条（已确认）、题目第 3 版、评分标准第 2 版"。老师可以增减参考材料。
- 这条提示**由上下文白名单和上游引用自动生成**，和模型实际看到的内容一致，不是另外写的说明文字。

## 5. 关键机制

### 5.1 产物与版本

- 产物确认后不再修改，改动即新版本，旧版本保留。
- 每份产物记录：类型、谱系编号、版本号、状态（`draft` 草稿 / `confirmed` 已确认 / `superseded` 已被取代）、内容和内容哈希、来源（`generated` 模型生成 / `edited` 老师修改 / `imported` 导入）、对应的模型调用记录。
- 老师编辑模型生成的内容后，保存修改前后的差异，用于研究"老师改了什么"。

### 5.2 上下文白名单

每类任务在代码里声明自己允许读取的产物类型和范围：

| 任务 | 允许读取 | 明确禁止 |
|---|---|---|
| 起草目标 | 项目背景、材料 | — |
| 出题 | 已确认的目标、材料、出题要求 | 学生作答 |
| 出题自检（解题） | 题干 | 参考答案、评分标准 |
| 批改 | 本题的题目、评分标准、参考答案，本学生本题的作答 | 该学生的其他作答和历史、其他学生的作答 |
| 学情分析 | 已确认的批改、目标、作答原文 | 老师已写好的学情结论（评测时） |

组装提示词的函数只能通过白名单取数据，并把实际取到的产物列表（编号、版本、哈希）写进调用记录。这样，产品上的"已参考"提示、研究上的"模型能看到什么"、工程上的依赖记录，三者来自同一份数据。

### 5.3 上游修改与过期

- 下游产物**固定在**它所依据的上游版本上，不会自动跟着变。
- 上游出现新版本时，老师要说明这次修改的性质：
  - **实质修改**（改了题意、答案、给分规则）：所有引用旧版本的下游产物标记为"依据已变化"，列在项目首页待处理；老师可以选择重新批改或保留原结果。
  - **文字修改**（改错字、措辞）：不触发过期，只记录。
- 过期沿上游引用关系传递：评分标准改了 → 相关批改过期 → 用到这些批改的学情分析也过期。
- 传递在老师确认的内容处停止：题目、评分标准、目标会被标记“依据已变化”，但不再往下传；学生作答永远不标记。否则修改第 1 轮的评分标准会经过“问题模式 → 巩固题”一路传到第 2 轮的批改，噪声太大（实现时发现，2026-11-18）。

### 5.4 给分

- 评分标准由若干要点组成，每个要点有分值，可以设部分得分。
- 批改按要点判定：得分、未得分或无法判定。"无法判定"的要点进入复核队列，不计入总分，直到老师处理。
- 总分由服务器把各要点的得分加起来，不让模型直接给总分。

## 6. 批改的可靠性（从现有代码迁移）

沿用现有判定机制，但改成**与学生会话无关的纯函数**：

```
grade(题目, 评分标准, 参考答案, 作答) → 批改结果
```

流程：

1. **工具验证（能用时）。** 代数等价、数值、单位等确定性检查。工具能覆盖整道题时，以工具结论为准。
2. **模型逐要点判定。** 每个要点的判定都必须引用作答原文，服务器核对引用，允许宽松匹配（全角半角、空白、引号）。引不出原文就重试一次，仍失败则这个要点标为"无法判定"。
3. **低置信度视为无法判定。**
4. **交叉复核：只针对"高置信度、引用核对通过的失分判定"。** 由**不同厂商的模型**独立再判一次。复核模型看到的内容和主判相同，但看不到主判的结论。两个模型都判失分才采纳，有分歧就交给老师。一份作答中有多个失分要点时，只调用一次复核模型，把这些要点一起再判。
   - 判得分且高置信度、引用核对通过的，直接采纳，不复核。
   - 低置信度、引用核对不过、工具结论与模型冲突的，直接转老师，不经过复核模型。
   - 写作题不复核，建议分一律由老师确认。
   - **抽检：** 每批批改随机抽约 5% 判得分的作答交给复核模型，用来监控"把错答判成得分"的比例。高利害场景（如考试）可以打开"全部复核"开关。
5. **复核风险标记。** 对以下情况标记风险：负面判定没有复核确认、低置信度、参考答案由模型生成且老师还没确认、工具结论与模型判定冲突。待复核队列按风险排序。
6. **老师改判。** 生成新的批改版本，触发下游过期。

### 6.1 按题型选择判定方式

同一套批改流程适用于所有科目，区别在于**第 1 步用什么工具、模型判定的权重有多大、结果能否直接计分**。

| 题型 | 主要科目 | 判定方式 | 可靠程度与界面处理 |
|---|---|---|---|
| 选择、判断、多选 | 全部 | 服务器按答案直接比对，不调用模型 | 确定，直接计分 |
| 填空（短答案） | 全部 | 先规范化再比对：数学表达式判等价、数值允许误差、核对单位、化学式规范化、老师给的可接受答案；比对不上再由模型判定 | 高 |
| 计算与推导 | 数学、物理、化学；人工智能中的计算（如准确率、召回率、信息熵、梯度） | 逐要点模型判定，加上工具验证（代数等价、数值、单位换算、化学方程式配平） | 高 |
| 简答与材料分析 | 思想政治、历史、地理、生物、语文阅读、人工智能概念题 | 按采分点判定，每点引用作答原文；材料题还要核对结论是否对应材料 | 中，负面判定进入复核 |
| 英语语言题（改错、语法填空、翻译） | 英语 | 先按答案比对，再由模型判断是否属于可接受的其他写法 | 中高 |
| 写作 | 语文作文、英语写作 | 按维度分档（如内容、结构、语言），每个维度引用原文说明理由，给出**建议分** | 低，**必须老师确认**后才计分 |
| 实验设计、读图 | 物理、化学、生物、地理 | 按采分点判定；题目或作答含图片时用多模态输入 | 中，负面判定进入复核 |
学科包需要的新工具：答案比对与规范化（全科）、单位换算和数值误差（物理、化学、人工智能中的计算）、化学方程式配平检查（化学）。

人工智能科目**暂不出编程题**，只出知识题，例如机器学习中的支持向量机、决策树、神经网络等概念和原理。所用题型就是上表中的选择、填空、简答和计算，因此不需要编程沙箱。以后如果要加编程题，再补沙箱（隔离容器、禁止联网、限制时间和内存）。

关于学科资源：
- 知识点库 K12-KGraph 只覆盖人教版数理化生，其他科目的教学目标直接来自老师的材料，知识点打标作为可选功能。
- 英语科目的作答是英文，反馈语言由学科包配置，默认中文讲解，引用原文保持英文。

### 6.2 从现有代码迁移

需要迁移的部分：`core/evidence.py`（引用核对）、`grading/assessment.py`、`grading/criteria.py`、`grading/algebra.py`、`resources/toolbox.py`，以及 `grading/engine_grading.py` 中与会话无关的逻辑。迁移后**必须去掉**现在评分上下文里的学习记忆、以往的错误假设等学生历史信息。

## 7. A/B 选择

- **出现在哪里：** 出题和（第二期的）讲评稿。不是每次都出现，默认按一定比例触发（初始建议 20%），比例可以配置。
- **两份候选只差一个因素**（换模型，或换提示词版本），并记录这个因素，否则老师的选择无法解释。
- **左右位置随机**，并记录下来。
- **老师的选项：** 采用 A、采用 B、差不多、都不合适；理由选填，可以跳过。选中后可以直接编辑，然后点"采用此版，进入下一步"。
- **数据性质：** 老师的选择是**偏好数据**，不是正确性数据。研究记录里单独标记一条数据"是否经过独立复核"，进入 benchmark 前必须经过复核。

## 8. 模型接入

### 8.1 网关

- 地址 `https://lightingtheword.com/v1`，兼容 OpenAI 的 `/chat/completions`；部分模型也支持 Anthropic 和 Gemini 的原生接口。
- 截至 2026-11-18，网关上有 64 个模型，包括 GPT-5.x/6.x、Claude、Gemini、DeepSeek、GLM、Kimi、Qwen、MiniMax 等系列。
- **密钥只从环境变量 `EDU_LLM_API_KEY` 读取**，不写进代码、配置文件和文档，也不提交到仓库。地址用 `EDU_LLM_BASE_URL` 配置。

### 8.2 按角色配置模型

不同步骤用不同的模型，通过配置文件指定，代码里不写死模型名：

| 角色 | 用途 | 要求 |
|---|---|---|
| `generator` | 起草目标、出题 | 生成质量高 |
| `grader` | 批改主判 | 结构化输出稳定，判定准确 |
| `reviewer` | 交叉复核、出题自检里的解题 | **与 grader 不同厂商**，避免同源偏差 |
| `analyst` | 学情分析 | 长上下文，能遵守引用要求 |
| `judge` | 离线评测的裁判 | 与被评测的模型不同厂商 |

**当前选择（2026-11-18）：开发阶段 `generator`、`grader`、`analyst` 统一使用 `DeepSeek-V4.1-Flash`。** 依据是中文数学判定集全量测试（392 份，给参考答案）：错误解答被判为正确 3.6%，正确解答被判为错误 7.8%，输出格式合格 388/392，引用原文可核对 99.7%，延迟中位数 4 秒。

另外两项测试：
- **多学科：** 现有的 5 科判定集（语文、英语、物理、化学、生物，共 166 份，由模型生成，题目偏简单）上，输出格式合格 164/166，错误解答被判为正确 1/83，正确解答被判为错误 0/81。
- **看图：** 能读出截图中的文字，两个后端都支持图片输入。手写作答的识别还没测。

注意：这个模型会先推理再回答，推理过程也计入输出上限。看图测试中，上限设为 400 时推理就把额度用完了，返回空内容。批改调用的输出上限至少设为 3000。

**`reviewer` 使用 `qwen3.8-flash`（2026-11-18 确定）。** 复核规则：**只复核负面判定**。主判模型判为错误时，由复核模型再判一次；两者都判错误才采纳，有分歧就交给老师。主判为正确的直接采纳；低置信度或引用核对不过的，直接转老师。

同一判定集上的测试：
- **格式和速度：** 输出格式合格 392/392，没有出现 qwen3.8-27b 那样返回数组的情况；延迟中位数 8.9 秒，是 DeepSeek 的两倍左右。因为只复核负面判定，影响可以接受。
- **按上述规则模拟：** 错误解答被判为正确 3.6%，正确解答被判为错误 4.6%，转老师 4.1%。

**这个数据集几乎测不出复核的作用。** DeepSeek 的 7 个"错判为对"，Qwen 全部也判错；15 个"对判为错"里有 14 个两者都错。抽查发现，这些"两者都错"的题目多数是**数据集的标注问题**：翻译时把题意弄反、参考答案错误，或者被标为正确的学生解答里本身有表述错误。也就是说，两个模型的判断其实是对的。复核模型的真实效果，要在第 11 节新建的高中评测集上衡量。这些两个模型一致反对原标注的题目，要交给人工重新标注。

**也测过 Claude Sonnet 5.5，因成本未采用。** 它需要走 Anthropic 原生接口（`/v1/messages`），用 `output_config.format` 约束输出：OpenAI 兼容接口会忽略格式要求，强制工具调用也不被支持。同一判定集上：
- 只采纳高置信度、引用核对通过的判定后，错判为对 1.5%，对判为错 2.0%，转老师 11%。
- 它在有标注问题的题目上多半给低置信度，置信度最可靠。
- 用"Sonnet 主判 + DeepSeek 复核"，两类误判都可以降到 1.5%。

以后如果预算允许，或者有高利害场景，可以考虑它。

所有角色的模型都通过配置指定，以后更换时不需要改代码。

### 8.3 结构化输出：2026-11-18 实测

用同一个简单判定请求测试 `response_format: json_schema`（strict）的结果：

| 模型 | 结果 |
|---|---|
| gpt-5.4 | 严格符合 schema |
| DeepSeek-V4.1-Flash | 中文判定集 392 份中 388 份符合 schema；其余 4 份为空输出，或在 JSON 之后输出大量空白直到长度上限 |
| gemini-3.1-pro-preview、DeepSeek-V4-Pro-0813、glm-5.3 | 返回合法 JSON 对象，这次符合 schema；是否在服务端强制执行约束未确认 |
| qwen3.8-27b | **返回了数组**，不是要求的对象 |
| claude-sonnet-5-5（OpenAI 接口） | **忽略了 `response_format`**，返回 Markdown 文本 |

由此确定的做法：

1. **不信任网关的约束解码。** 所有结构化输出都用 pydantic 校验；不合格时把错误信息发回模型修复一次，仍不合格则视为调用失败。现有代码已有这套机制，直接沿用。
2. **按厂商选择调用方式。** OpenAI、Gemini、DeepSeek、GLM 系列用 `json_schema`；Claude 系列改走 Anthropic 原生接口，用强制工具调用来获得结构化输出。
3. **记录网关实际返回的模型版本。** 例如请求 `gpt-5.4`，实际返回的是 `gpt-5.4-2026-03-05`，研究记录里两者都要保存。
4. **超时与重试。** 每次调用设置超时；网络错误和限流时退避重试。判定类调用失败时不能悄悄降级为别的结果，而是返回"暂不可用"，由老师稍后重试。
5. **同一个模型名可能对应多个后端版本。** 例如请求 DeepSeek-V4.1-Flash 时，392 次调用中返回了两个不同的版本标识（`deepseek-v4.1-flash-1017` 和 `deepseek-v4-1-flash-261017`），从响应头判断，前者经阿里云百炼（DashScope）提供，后者很可能经火山方舟提供，网关在两者之间负载均衡；版本日期相同，实测判定行为一致。即便如此，每次调用仍要单独记录返回的版本，以便后端变化时能追查。
6. **成本。** 记录每次调用的 token 用量（网关会返回 `usage`），按项目汇总，便于估算批改一个班需要多少成本。

## 11. 评测（教师端）

现有评测主要针对学生辅导，教师端需要新建。所有评测数据**按材料家族切分**开发集和测试集，同一家族不能同时出现在两边。

| 评测 | 指标 | 数据来源 |
|---|---|---|
| 批改准确性 | 把错答判为正确的比例、转老师比例、要点级别的一致率、总分平均误差 | 先用现有的 StepVerify 和中文数学判定集（英文 400 份、中文 392 份），再加入老师标注的真实作答 |
| 出题质量 | 参考答案正确率（由解题自检和人工抽查得出）、老师直接采用率、老师的修改幅度、题目与目标的对应程度 | 教师试用记录 |
| 学情分析 | 每个问题模式能否被其引用的作答支持（人工判定）、是否出现没有证据的结论 | 教师试用记录加人工标注 |
| 流程衔接 | 上游修改后，过期标记是否完整、是否误报 | 自动化测试 |
| 闭环效果 | 被巩固练习针对的问题模式在第二轮的复现率，与未被针对的问题模式对比 | 教师试用中的两轮作答 |

**各学科的评测数据现状：**

| 科目 | 现有数据 | 缺口 |
|---|---|---|
| 数学 | 中文判定集 392 份 | 题目是翻译过来的小学应用题，**不是高中难度** |
| 语文、英语、物理、化学、生物 | 多学科集各约 30 份 | 由模型生成，偏简单；没有作文和写作题 |
| 思想政治、历史、地理、人工智能 | 无 | 全部需要新建 |

第 0 期要为每个科目建一个小评测集，起步每科约 60 份，正确和错误作答各半，覆盖该科的主要题型。可能的来源：
- 公开的高考题集（如 GAOKAO-Bench）：需要核实许可，并注意这些题可能已经出现在模型的训练数据里，结果会偏乐观；
- 老师提供的真实作答，由老师标注判定结果；
- 模型生成后经老师审核的作答。

写作题需要老师给出分档，用来衡量建议分和老师打分的差距。

**第 0 期必须先跑批改准确性**，用它来选定 `grader` 和 `reviewer` 的模型，并且证明迁移后的判定没有变差。

报告时分两种运行方式（需求文档第 4 部分）：**单任务评测**（所有模型拿到相同的、老师确认过的上游产物）和**完整闭环评测**（模型用自己前面步骤的结果继续工作；记录中途的人工介入）。

## 12. 与 coursemaker 的对接

coursemaker 已经有的，我们直接复用：

- 账号体系；
- 每门课的课时结构：`lessonPlan`（教学大纲）、`handout.md`（讲义）、`knowledgePoints`（知识点，Markdown 格式）；
- 计费：`credits_costs.json`，`credits.ensure_can_charge` / `charge`；
- 调用记录：`generation_records`，在路由上加 `@capture(action, entry=True)`。

对接方式：

- **入口：** 每个课时下新增"练习与批改"面板，不插入它现有的 8 步流水线。
- **上游：** 从 `lessonPlan` 和讲义中提取教学目标，老师确认后成为 `objective` 产物。引用时记录这些文本的哈希；文本变化后提示目标可能需要更新。
- **数据：** 存在独立的表中，通过 `course_id`、`chapter_id`、`user_id` 关联，不写入 `course.json`。
- **模型：** 判定需要第 8 节的结构化输出和校验。可以给它们的 `text_models` 增加一个网关提供方，也可以由我们的客户端调用、手动计费并套上 `capture`。前者需要对方同意，先和维护者商量。
- **代码约束：** 新建路由模块 `server/routes/edu.py`（不往 3787 行的 `courses.py` 里加）；`edu_core` 是同步代码，在异步路由中用线程池调用；前端用 React 编写，文案放进 zh-CN 和 en 两个语言文件，因为它们的测试不允许新增写死的中文；PR 提到 `develop` 分支。
- **第一个 PR 的范围：** 确认教学目标 → 出题与出题自检 → 老师编辑并确认版本。批改和学情放到后续 PR。

## 14. 风险与待定问题

**需要尽快决定的：**

1. **评测数据从哪里来。** 思想政治、历史、地理、人工智能目前完全没有评测数据，写作题也没有。是否有合作老师能提供真实作答和标注？
2. **作答导入格式。** 首版只支持表格和单张照片，是否够用？老师手上实际的作业是什么形式？
3. **学生数据的授权与去标识。** 作答来自未成年人。需要确定知情同意的方式；系统只存学生代号，导出研究数据前需要再做一次去标识检查。
4. **模型选型和成本上限。** 由第 0 期评测决定；需要给出一个班一次批改的预算上限。

**已知风险：**

- 网关上的模型版本可能随时更新，同样的请求在不同时间结果不同。缓解方法：记录实际返回的模型版本；评测时固定版本，并定期重跑回归。
- 开发阶段依赖外部网关，作答内容会发送到第三方服务。正式使用真实学生数据前，需要确认这符合授权范围。
- 出题自检和交叉复核会让每道题、每份作答的模型调用次数翻倍，需要在第 0 期测算成本。
- 写作类批改的可靠性明显低于其他题型，只能给建议分；如果老师把建议分直接当成绩，会有误导。界面需要明确标注，并且必须由老师确认后才计分。
- 覆盖 10 个科目会让首版工作量明显增加。如果时间紧，可以先保证所有科目的客观题、填空和简答题，写作稍后跟上。


## 课程标准约束（2026-11-19，数学试点）

- 课标条目由 `scripts/edu_build_curriculum.py` 从教育部官方 PDF（课标合集 zip，见文件内 `source_url`）抽取，存为 `edu_core/curriculum/math.json`：内容要求 154 条、学业要求 29 段、教学提示 40 段、单元说明 29 段。每条记录页码，并用程序核对是规范化后 PDF 文本的逐字子串；PDF 本身不入库，只记 sha256。选修课程未收录。PDF 中的选学图标转成 `optional` 标记。
- 匹配：知识模块 + 本课时内容，按 2–4 字片段做 IDF 加权匹配，条目自身标题权重高于所属单元名。老师没有手动选择时，生成前自动选得分不低于最高分 75% 的条目（最多 4 条，不选选学条目），并保存为 `chosen_by: auto`，老师可见可改；课时信息变化时自动选择会重做，老师的选择不会被覆盖。
- 生成约束：提示词要求每条目标填 `standard_ids`、要求不高于课标用词、遵守学业要求和教学提示；超出课标须 `beyond_standard` + 理由。服务器丢弃不在提供范围内的编号，并用动词等级（了解/知道 < 理解 < 掌握/熟练）检查目标是否高于所引条目，结果写入目标的 `checks`；引用条目原文快照写入 `standard_refs`。
- 出题时也带上本课时内容和所引条目所在主题的教学提示（如“避免编制偏题、怪题”）。
- 上下文白名单：`draft_lesson_plan`、`generate_questions` 新增 `curriculum`，“已参考”显示“课程标准 N 条”。

## 出题改题：题目审核、目标覆盖、换题（2026-11-19）

- 题目审核（`review_question`，reviewer 角色）：输入题目、参考答案、评分要点，以及对应目标与达成标准、本课时内容、目标所引课标条目原文、学生基础、要求难度（再练题还有针对的问题模式）。输出是否考查目标、是否超范围（前置知识可用）、估计难度、题目问题。服务器转成 `checks.flags`（与目标不符 / 超出范围 / 难度偏高或偏低 / 题目问题）和 `checks.difficulty`。上下文白名单 `review_question`: question_stem、lesson_plan、curriculum。审核失败只记一条提示，不阻断出题。
- 题目内容新增 `difficulty_requested`、`purpose`；换题的版本另记 `regenerated_from`、`instruction`。
- 目标覆盖 `coverage(pid, round)`：按已确认方案的目标统计本轮题数、确认数、待核对题号（答案存疑或有审核问题），以及没有对应目标的题。
- 换一道 `regenerate_question(qid, instruction, difficulty)`：同题型、同目标（再练题同问题模式），告诉模型原题和老师要求；新题经自检与审核后存为同一题目谱系的新版本（题号不变），评分标准也存为原评分标准谱系的新版本。确认规则不变，改已确认题目时仍要选修改性质。
- 采用独立解题答案 `adopt_solver_answer(qid)`：选择/判断/填空题用解题模型的最终答案替换标准答案，参考答案换为其解答过程，存为新草稿版本。
- 题目列表按题号排序，题目修改或换题后位置不变。
